# 从这里开始

<p className="lede">
你有一个在生产环境跑的智能体。它调用工具，对客户的记录作出断言，也承诺去做某些事情。
它说的话里有一部分不是真的，它承诺的事情里有一部分从未发生。这一页讲的就是这件事，而
且你不需要采用一门新语言就能解决其中大部分。
</p>

## eleph 做什么

三件事，而且是刻意做窄的：

<Steps>
<li>
**它拒绝记录所不支持的断言。** 不是软化，不是记日志。`assert_answer` 会在文本抵达
客户之前抛出异常。
</li>
<li>
**它拒绝前置条件不成立的工具调用。** `require` 检查的是真正发生过的事情，而不是某个
可能有人忘了更新的字段。
</li>
<li>
**它记得你承诺过什么。**「您的退款已在路上」会变成一笔带期限的债务，运行结束时，
*我们兑现了吗* 这个问题是有答案的。
</li>
</Steps>

## eleph 不做什么

<Callout type="danger" title="它不会降低你的 token 账单">
本项目没有任何东西度量成本，所以这里也不宣称能改变成本。守卫不改写你的提示词，不增加
一次模型调用，也不重试任何东西。

能够被验证的是另一个方向：一个 `Guard` **不发起任何模型调用，也不发起任何网络调用**。
它是在读一份只追加的列表的 Python 代码。所以它也不会增加开销。

如果你的问题是账单，这是错的工具。如果你的问题是你无法判断智能体的哪些回答是真的，
请接着读。
</Callout>

它也不是提示词技巧，不是输出过滤器，更不是一个通过面板配置的策略引擎。输出过滤器读的
是文本。这个读的是历史。

## 度量究竟显示了什么

同一个智能体，在同样九个客服案例上跑两遍。模型相同，系统提示词相同，工具名称、描述和
签名都相同。唯一的差别是那两个会写入的工具底下有没有守卫。

| | 没有 eleph | 有 eleph |
|---|---|---|
| Claude Haiku 4.5，每个案例 5 次 | **30/45** | **45/45** |
| Claude Opus 5，更早的 7 案例套件，每个 3 次 | **19/21** | **21/21** |

更强的模型失败得更少。方向是一样的。

这个结果里有三件事比总分更重要，也正是它们能告诉你，你的系统有没有这个问题：

**失败是集中的，不是分散的。** 九个案例里有六个在两边都是 5/5 通过。三个在没有守卫时
5/5 全败。这不是一个模型偶尔运气不好，而是一个模型在三件具体的事情上稳定地、并且合乎
情理地犯错。

**有一个案例 0/5：有人问了陌生人的账户。** 智能体查了，也如实回报了，每一次都是。提示词
里没有任何东西说不许这么做，客户的请求也完全清楚，回答是那个乐于助人的选择。

**有一个案例在没有守卫时 5/5 通过**，这一点和那些失败同样重要。系统提示词写了退款上限
是 200 雷亚尔、更大的金额要上报，案例本身很清楚，模型每一次都做对了。**关于一个毫不
含糊的案例的清晰指令是有效的。守卫不是为这些准备的。**

把三个失败和六个成功分开的不是难度。在那三个里，模型必须去怀疑某样东西：客户对过去的
说法、客户的坚持，或者客户到底有没有资格发问。模型被造出来就是为了不去怀疑。

[完整对照，以及它是伴着哪个 bug 建起来的 →](/docs/integration/langchain)

## 三种形态，由轻到重

你不必采用这门语言。这三种里有两种完全用不到它。

| 形态 | 你需要改什么 | 你得到什么 | 试一试的代价 |
|---|---|---|---|
| **observer** | 什么都不改，你只负责把事件喂给它 | 记录中什么为真，以及一份审计 | 一个下午 |
| **guard** | 断言和工具调用都经由它路由 | 没有依据的主张会抛出异常，而不是被发出去 | 一天 |
| **language** | 用 `.eleph` 编写处理器 | 静态证明 | 一周 |

先在你已有的流量上以 observer 的形态跑。它不可能弄坏任何东西，因为它什么都不强制执行。
如果它从来没和你的系统产生分歧，那你就没有这个问题，可以到此为止。

## 你要的是哪一种

<Callout type="note" title="如果拿不准，你要的是守卫">
**observer** 回答的是「我的智能体会说记录所不支持的话吗？」。在改任何代码之前，先拿它
跑一遍昨天的流量。

**guard** 是大多数系统真正上线的那一种。规则住在一个 `eleph check` 能证明的 `.eleph`
文件里；你的 Python 调用 `require`、`assert_answer`、`record` 和 `promise`。你完全
不写处理器。

**language** 适用于决策逻辑本身也需要被验证的场合，而不只是它读取的那些事实。那是研究
产物，也是唯一需要[语言参考](/docs/reference/program-structure)的一种。
</Callout>

把规则放在策略文件里、而不是用 Python 写检查逻辑，理由只有一句：**你的守卫在凌晨三点
执行的规则，和求解器证明过的是同一份产物。** 规则被证明过的守卫，和规则只是被某人相信
的守卫，是两回事。

## 从这里往下走

<Steps>
<li>
[**安装**](/docs/installation)到你的项目里。一个依赖，Z3。
</li>
<li>
[**接到你的模型上**](/docs/use/any-model) —— GPT-4、Claude，任何东西。守卫里没有任何
东西知道 LLM 是什么。
</li>
<li>
[**为你的领域建模**](/docs/use/modelling) —— 把你已有的表变成事件和事实，这是采用
eleph 唯一真正需要新思考的部分。
</li>
<li>
[**配合你的编程助手**](/docs/use/with-your-assistant) —— 一个把检查器而不是文档交给
你的模型的 MCP 服务器，这样它写出的策略是求解器证明过的。
</li>
<li>
[**API 参考**](/docs/python-api)，等你已经知道自己要找什么的时候。
</li>
</Steps>

如果你想先看到想法本身再谈集成，[快速上手](/docs/quickstart)是九行代码和一个 McCarthy
在 1998 年写下的 bug。
